# Deployment Guide - PTR ALUMNI NETWORK

This guide covers a complete Render deployment (static React frontend, Docker-based PHP REST API, and MySQL) plus the existing Apache and Docker alternatives. Render does not offer a managed MySQL service: its MySQL option is a self-managed Docker service with a persistent disk. For managed MySQL, use an external provider such as AWS RDS for MySQL; do not substitute PostgreSQL.

> Do not use Vercel or Netlify for the full stack: they cannot execute `api/index.php` or connect to MySQL through PDO. They can only host the static frontend.

---

## 1. Prerequisites

| Requirement | Minimum |
| --- | --- |
| PHP | 8.1 with `pdo_mysql`, `fileinfo`, `mbstring`, `allow_url_fopen` |
| MySQL / MariaDB | MySQL 8+ or MariaDB 10.4+ |
| Apache | 2.4 with `mod_rewrite` and `AllowOverride All` (or Nginx equivalent) |
| Node.js | 22 (build time only) |
| pnpm | 10.18.0 (build time only) |
| Initial administrator | Register an account and promote it with trusted database access |

## 2. Render.com (recommended deployment)

The repository includes [`render.yaml`](./render.yaml), [`Dockerfile.api`](./Dockerfile.api), and a MySQL initialization image. The Blueprint defines three separate services:

1. `ptrp-mysql`: private MySQL 8 Docker service with a persistent disk mounted at `/var/lib/mysql`.
2. `ptrp-api`: PHP 8.3 + Apache Docker web service with a persistent uploads disk mounted at `/var/data`.
3. `ptrp-frontend`: Vite-built Render Static Site with SPA fallback and a build-time API URL reference.

Persistent disks require a paid Render plan. The included MySQL service is self-managed and its disk is not a substitute for off-site database backups. For a managed MySQL database, provision it with an external provider and configure the API's `DB_*` environment variables instead.

### 2.1 Create the services

1. Push the verified deployment branch to GitHub. In the Render Dashboard, choose **New → Blueprint**, connect `honore63/PTR-Program`, and select branch `main`.
2. Review the services and environment variables from `render.yaml`, then apply the Blueprint. It creates the database, API, and frontend together; references ensure the private database and API are available to dependent services. If creating services manually instead, create the MySQL service first, then the API, then the static site.
3. Keep the generated `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, and `MANUS_JWT_SECRET` secret. Do not copy them into the repository, frontend variables, screenshots, or support requests.
4. Wait for the database, API, and frontend deploys. The MySQL image imports `database/ptrp.sql` only the first time its data directory is initialized; later deploys preserve the persistent database disk.
5. In **ptrp-api → Settings → Environment**, set `ALLOWED_ORIGINS` to the exact frontend origin (for example `https://ptrp-frontend.onrender.com`). If you attach a custom frontend domain, add that exact `https://` origin too. Do not include paths or a trailing slash.
6. If using a custom API domain, set `PUBLIC_API_URL` to its HTTPS origin and add `VITE_API_BASE_URL=https://<api-domain>/api/` to the static site's environment. The build uses this override when present; otherwise, the Blueprint wires the API hostname into the frontend build. Keep `ALLOWED_ORIGINS` in sync. The default `COOKIE_SAMESITE=Lax` works for the generated Render domains and custom domains under the same registrable domain; if the frontend and API are on different registrable domains, use `COOKIE_SAMESITE=None` with HTTPS on both.
7. Configure SMTP only when authorized credentials are available. Set `SMTP_USERNAME`, `SMTP_PASSWORD`, and `SMTP_FROM_EMAIL` on `ptrp-api`; these are backend-only secrets. Social integration credentials are optional and should also be set only on the API service.

### 2.2 Environment variables

The Blueprint creates the primary variables. Configure or verify these in **ptrp-api → Environment**:

| Variable | Value / source |
| --- | --- |
| `DB_HOST` | Private hostname from `ptrp-mysql`, supplied by the Blueprint; use the external provider hostname if using external MySQL |
| `DB_PORT` | `3306`, or the provider's MySQL port |
| `DB_NAME` | `ptrp` |
| `DB_USER` / `DB_PASSWORD` | Dedicated app database user and secret; generated by the Blueprint for its MySQL service |
| `DB_SSL_CA` | Optional path to the MySQL provider's CA certificate file when TLS certificate verification is required |
| `MANUS_JWT_SECRET` | Generated by Render; keep at least 32 characters and backend-only |
| `BASE_PATH` | `/` |
| `ALLOWED_ORIGINS` | Comma-separated exact frontend origins, including `https://` |
| `UPLOAD_DIR` | `/var/data/uploads`; keep the API disk mounted at `/var/data` |
| `COOKIE_SAMESITE` | `Lax` |
| `APP_ENV` | `production` |
| `PUBLIC_API_URL` | Optional; set to the API's HTTPS origin when using a custom API domain |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_ENCRYPTION` | Optional SMTP provider; the API defaults to Gmail / 587 / TLS |
| `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL` | Authorized SMTP sender credentials; backend secrets only |

The frontend's `VITE_API_BASE_URL` is generated during the static build from the `ptrp-api` service reference. Never set database, JWT, SMTP, or other private credentials as `VITE_*` variables: Vite publishes those values in browser JavaScript.

If connecting an external managed MySQL database, create a MySQL 8-compatible `ptrp` database and dedicated least-privilege app user, restrict database ingress to Render's permitted outbound addresses or a private connection, and configure the provider's TLS CA. Before applying the Blueprint, remove the `ptrp-mysql` service and `ptrp-database` environment group, remove the API's `fromGroup` and `DB_HOST` service reference, then configure the API variables like this:

```yaml
      - key: DB_HOST
        sync: false
      - key: DB_PORT
        value: "3306"
      - key: DB_NAME
        value: ptrp
      - key: DB_USER
        sync: false
      - key: DB_PASSWORD
        sync: false
      - key: DB_SSL_CA
        value: /etc/secrets/mysql-ca.pem
```

Set the `sync: false` values in Render's protected service environment and upload the provider CA certificate as an API **Secret File** at the configured path. Never put credentials or private keys in the Blueprint or GitHub. Render's managed PostgreSQL is not compatible with this PHP API.

### 2.3 Database bootstrap, upgrades, and migrations

- **New Blueprint database:** MySQL initializes `ptrp` from `database/ptrp.sql` on an empty persistent disk. This seeds the current schema and existing public content, including 17 model schools, 3 news articles, 11 gallery entries, and Honore Tuyishime's featured alumni profile. It does not create an administrator. The initial import runs only on an empty data directory.
- **Existing database:** take and verify an off-service backup first. Do not re-import `ptrp.sql` into a live database. From the API service's Shell/SSH session, run the unapplied migrations individually with the migration runner. For a legacy installation, the normal upgrade sequence is:

```sh
php /usr/local/bin/ptrp-migrate 20261105_website_cms.sql
php /usr/local/bin/ptrp-migrate 20261105_contact_messages.sql
php /usr/local/bin/ptrp-migrate 20261106_feature_honore_tuyishime.sql
php /usr/local/bin/ptrp-migrate 20261106_sync_public_content.sql
php /usr/local/bin/ptrp-migrate 20261106_editor_member_roles.sql
php /usr/local/bin/ptrp-migrate 20261106_admin_notifications.sql
php /usr/local/bin/ptrp-migrate 20261107_page_analytics.sql
```

  Run only migrations not already applied. For databases that already contain resident profiles, `20261106_sync_public_content.sql` expects the resident-teacher schema and Honore profile to exist; apply the preceding migrations first. Review each SQL file and back up immediately before applying it. These content migrations are deliberately manual; deployments do not automatically run them (the API only performs its existing `users`-table compatibility checks at startup).
- **Administrator setup:** register the intended administrator through `/portal`, then use Render Shell/SSH to connect to the private MySQL service, run `mysql -u root -p ptrp`, and promote that exact email with `UPDATE users SET role = 'admin' WHERE email = 'your-admin@example.com';`. Enter the root password from the MySQL service's secret environment when prompted, verify exactly one intended row changed, then sign in through `/portal`. Never use a default or shared admin password.
- **Backups:** schedule `mysqldump --single-transaction` to storage outside Render and independently back up `/var/data/uploads`. Render disk persistence protects files across deploys, not against loss or corruption. Test restoring both the database and uploaded files.

### 2.4 Deployment verification

Do not treat a successful build as a production test. After deployment, verify:

1. Open the Render Static Site URL and directly refresh `/`, `/residents`, `/news`, `/gallery`, `/network`, and `/portal`; the static rewrite should return the SPA.
2. Request `https://<api-host>/api/health`; it must report a healthy database connection. A failing health check means the API is not ready.
3. Check `SELECT COUNT(*) FROM schools;` (expected 17) and confirm the three named migration news slugs, 11 gallery records, and Honore's row without duplicates.
4. Register a test resident, sign in as the provisioned administrator, approve it, and verify it appears in the public directory. Test administrator login and profile editing.
5. Create or edit news, gallery, and school entries in Admin Portal and confirm the published changes appear publicly after refresh.
6. Upload a test image/document, verify it loads from the API host, redeploy the API, and verify the same URL still works.
7. Test desktop and mobile layouts and inspect browser/network errors. Verify HTTPS, the secure authentication cookie, and CORS behavior from the actual frontend origin.
8. Test contact-email delivery only after authorized SMTP credentials are configured. The contact inbox can retain messages when SMTP is unavailable.

No Render deployment or production URL is claimed as live until these steps have actually been run against the deployed services.

## 3. Database setup (manual hosting)

1. Create the database and a least-privilege user:

```sql
CREATE DATABASE IF NOT EXISTS ptrp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'ptrp'@'%' IDENTIFIED BY 'REPLACE_WITH_A_STRONG_RANDOM_PASSWORD';
GRANT ALL PRIVILEGES ON ptrp.* TO 'ptrp'@'%';
FLUSH PRIVILEGES;
```

2. Import the schema:

```bash
mysql -u ptrp -p ptrp < database/ptrp.sql
```

The script is idempotent (`CREATE TABLE IF NOT EXISTS`) and creates all application tables, indexes, and foreign keys.

It does not create an administrator account. Register the intended administrator at `/portal`, then promote that exact account using a trusted database session:

```sql
UPDATE users SET role = 'admin' WHERE email = 'your-admin@example.com';
```

Replace the example address and verify the affected row. Never grant admin based on an unverified email or account-registration order.

For databases created by older revisions, audit any existing administrator accounts, replace previously shared or reused passwords, and invalidate sessions before public deployment. Re-importing the updated schema does not alter existing user records.

3. Verify:

```sql
USE ptrp;
SHOW TABLES;
```

Expected tables include `users`, `siteContent`, `mediaAssets`, `schools`, `teachers`, `alumni`, `newsArticles`, `galleryItems`, `bestPractices`, and `contactMessages`.

For an existing database, take a fresh backup and apply `database/migrations/20261105_contact_messages.sql`. This creates the message inbox without replacing existing tables or content. Do not skip the backup.
To publish the featured Honore Tuyishime resident-teacher profile on an existing installation, back up the database and apply `database/migrations/20261106_feature_honore_tuyishime.sql`. The supplied portrait is bundled with the frontend as `client/public/honore-tuyishime.png`; administrators can replace it from the Resident Teachers editor.
To sync the published news archive and gallery photos with the Admin Portal, and mark Honore's resident profile as an alumni-network member, back up the database and apply `database/migrations/20261106_sync_public_content.sql`. The migration inserts missing records only; it does not overwrite existing administrator edits or import the old placeholder alumni profiles.

## 4. Configuration

### 4.1 PHP configuration

Copy the template and edit it:

```bash
cp config.php.example config.php
```

Set at minimum:

| Key | Value |
| --- | --- |
| `db_host` | MySQL host (e.g. `127.0.0.1` or the managed DB hostname) |
| `db_port` | `3306` |
| `db_name` | `ptrp` |
| `db_user` | Database user |
| `db_password` | Database password |
| `base_path` | URL base path (`/` for a domain root, `/PTRP` for a subfolder) |
| `manus_jwt_secret` | HS256 signing secret, at least 32 cryptographically random characters |
| `smtp_host` | SMTP hostname; use `smtp.gmail.com` for Gmail |
| `smtp_port` | `587` for STARTTLS, or `465` for implicit TLS |
| `smtp_encryption` | `tls` for port 587 or `ssl` for port 465 |
| `smtp_username` | Authorized SMTP sending account |
| `smtp_password` | SMTP/app password (server-side only) |
| `smtp_from_email` | Optional verified sender; defaults to `smtp_username` |
| `smtp_from_name` | Optional sender display name |

`config.php` is gitignored and must never be committed.
Set `manus_jwt_secret` to at least 32 cryptographically random characters. Older deployments must replace the sample signing secret and invalidate existing sessions.

The deployed PHP API uses email/password authentication and does not require an OAuth callback. Manus OAuth settings are used only by the separate Node scaffold.

Contact submissions are delivered to `ptrpresidenteachers100@gmail.com`. For Gmail SMTP, enable 2-Step Verification and use an app password for `smtp_password`; standard account passwords may not work. Store credentials only in the protected `config.php` or hosting-provider secret settings. Never expose them in frontend code or `VITE_*` variables. The API stores each valid message before attempting delivery, so an SMTP outage is visible in the Admin Portal inbox and administrators can retry after fixing configuration. A successful response means the SMTP server accepted the message, not that the recipient mailbox confirmed delivery.

## 5. Build the frontend

```bash
corepack enable
pnpm install --frozen-lockfile
```

Choose the base path that matches `base_path` in `config.php`:

```bash
# Domain root (base_path = /)
pnpm exec vite build --base=/ --outDir dist/public --emptyOutDir

# Subfolder (base_path = /PTRP)
pnpm build:static
```

## 6. Deploy files

Upload to the document root that serves your domain:

```
document-root/
├── .htaccess
├── index.html
├── assets/
├── about/, news/, ...   (generated route folders)
├── api/
│   └── index.php
├── config.php
├── manus-storage/
├── partners/
├── resources/
└── uploads/            (writable by PHP)
```

Steps:

1. Upload the contents of `dist/public` (or `PTRP/`).
2. Upload the `api/` folder and root `.htaccess`.
3. Upload your configured `config.php`.
4. Create `uploads/`, copy `uploads/.htaccess` into it, and grant the PHP service account write access.
5. Ensure `config.php` is not world-readable.

### 6.1 Nginx (alternative to Apache)

If your host uses Nginx, apply the equivalent of `.htaccess`:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
location ^~ /api/ {
    try_files $uri /api/index.php?$query_string;
}
location ^~ /manus-storage/ {
    try_files $uri /api/index.php?$query_string;
}
location = /config.php { deny all; }
```

## 7. Docker deployment (single container / local testing)

The included `Dockerfile` builds the frontend and runs Apache + PHP in one container. MySQL is provided by the `db` service in `docker-compose.yml`.

```bash
# Local / test
cp .env.example .env
# Set MYSQL_PASSWORD, MYSQL_ROOT_PASSWORD, and MANUS_JWT_SECRET in .env before starting.
docker compose up --build
# App: http://localhost:8080
```

For other Docker-capable hosts, use the single-container image or adapt the configuration to the provider. Render uses the separate services described above. Set these environment variables:

```
DB_HOST=<managed mysql host>
DB_PORT=3306
DB_NAME=ptrp
DB_USER=<user>
DB_PASSWORD=<password>
BASE_PATH=/
MANUS_JWT_SECRET=...
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_ENCRYPTION=tls
SMTP_USERNAME=<authorized sending account>
SMTP_PASSWORD=<SMTP/app password>
SMTP_FROM_EMAIL=<optional verified sender; defaults to SMTP_USERNAME>
SMTP_FROM_NAME=PTR Alumni Network
```

The container generates `config.php` from these variables on startup and imports nothing automatically - import `database/ptrp.sql` into the managed database first.
For local Docker Compose, set the SMTP variables in `.env` before starting the container. Gmail requires 2-Step Verification and an app password; configure these values as protected deployment secrets in production. Never put SMTP credentials in frontend or `VITE_*` variables.

## 8. Production testing checklist

- [ ] `GET /api/auth/me` returns `null` (200) when signed out.
- [ ] Sign in through `/portal` or `/admin` redirects back successfully.
- [ ] `/admin` shows the dashboard after sign-in with the administrator account.
- [ ] Create a school, teacher, alumni record, news article, gallery item, and best practice; confirm they persist after reload.
- [ ] Upload an image through the admin media library; confirm it appears under `/uploads/`.
- [ ] Publish a news article; confirm it appears on `/news`.
- [ ] Open `/`, `/about`, `/network`, `/gallery`, `/resources`, `/contact` on desktop and mobile widths.
- [ ] Submit a contact message using authorized SMTP credentials; confirm it appears in the Admin Portal inbox and that the SMTP server accepts delivery to `ptrpresidenteachers100@gmail.com`. Confirm mailbox receipt separately.
- [ ] With SMTP unavailable, submit a contact message and verify the form reports email failure while the message remains available in the Admin Portal; restore SMTP and retry it from the inbox.
- [ ] Verify unauthenticated requests to `/api/admin/contact-messages` are rejected and duplicate submission IDs do not create or resend messages.
- [ ] Verify HTTPS is active and the session cookie is marked `Secure`.
- [ ] Confirm `config.php` returns 403/404 when requested directly.
